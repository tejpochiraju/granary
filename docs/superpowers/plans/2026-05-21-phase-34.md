## Task 1: PRAGMA recursive_triggers

**Background:** Phase 33 added nested trigger firing with a recursion limit of 32. SQLite gates this behavior behind `PRAGMA recursive_triggers` (default **OFF** in real SQLite). Sqlocaml currently always recurses. Task 1 introduces the gate.

**Decision:** Default the flag **ON** in sqlocaml (preserving current behavior). Real SQLite defaults OFF; we deliberately diverge — applications relying on sqlocaml's current behavior shouldn't break. This is documented as an intentional divergence.

**Files:**
- Modify: `lib/catalog/catalog.ml` / `.mli` — add `recursive_triggers : bool` flag and `get/set` helpers
- Modify: `lib/sql/ast.ml` — add `Pragma_recursive_triggers` and `Pragma_recursive_triggers_set of bool`
- Modify: `lib/sql/parser.mly` — wire PRAGMA names to the new AST nodes (read and write)
- Modify: `lib/sql/plan.ml` — `Op_pragma_get_recursive_triggers`, `Op_pragma_set_recursive_triggers of { on : bool }`
- Modify: `lib/sql/planner.ml` — translate AST → Plan
- Modify: `lib/sql/sema.ml` — bind these pragmas
- Modify: `lib/sql/exec.ml` — implement both ops; reuse the `Op_pragma_set_fk` pattern at line ~3699
- Modify: `lib/db/db.ml` — gate `fire_trigger_stmt` recursion: if depth > 0 and `recursive_triggers` is OFF, short-circuit (return `Lwt.return_unit`)
- Test: `test/test_e2e.ml` — new group `phase34_recursive_triggers`

```ocaml
let rec fire_trigger_stmt t stmt =
  if t.trigger_depth >= max_trigger_depth then
    Lwt.fail_with (Printf.sprintf
      "trigger recursion limit (%d) exceeded" max_trigger_depth)
  else if t.trigger_depth > 0 && not (Sql.Catalog.get_recursive_triggers t.catalog) then
    Lwt.return_unit  (* recursion disabled by PRAGMA; nested DML inside a trigger body doesn't fire further triggers *)
  else begin
    ...
  end
```

The condition `trigger_depth > 0` ensures the top-level trigger still fires; only nested invocations are gated.

## Task 2: Transitive cascade SET NULL / SET DEFAULT recursion

**Background:** In `lib/sql/exec.ml`, `cascade_delete_row_in_tx` (~line 2422) and `cascade_update_col_in_tx` (~line 2543) are mutually recursive. The CASCADE branches correctly recurse — they call `cascade_delete_row_in_tx` / `cascade_update_col_in_tx` for each affected child row. The SET NULL and SET DEFAULT branches call `update_col_in_tx` directly, which only updates that one child row and does NOT trigger further cascading.

**Fix:** Replace the direct `update_col_in_tx` calls in SET NULL / SET DEFAULT branches with `cascade_update_col_in_tx`. That helper sets the column value AND triggers further cascade actions on the descendents.

**Files:**
- Modify: `lib/sql/exec.ml` — replace `update_col_in_tx` with `cascade_update_col_in_tx` in 4 sites (two each for the DELETE-side and UPDATE-side cascade)
- Test: `test/test_e2e.ml` — new group `phase34_transitive_setnull`

### Steps

- [ ] **Step 2.1: Audit the four sites.** Run:

```bash
grep -n "update_col_in_tx" lib/sql/exec.ml
```

Identify which are inside SET NULL / SET DEFAULT branches of `cascade_delete_row_in_tx` and `cascade_update_col_in_tx`.

- [ ] **Step 2.2: Replace.** For each SET NULL site:

Before:
```ocaml
Lwt_list.iter_s (fun (crid, crow) ->
  update_col_in_tx tx cat child_meta ~rowid:crid ~row:crow
    ~col_idx:child_col_idx ~new_val:Row.V_null
) child_rows
```

After:
```ocaml
Lwt_list.iter_s (fun (crid, crow) ->
  cascade_update_col_in_tx tx cat clock params child_meta ~rowid:crid ~row:crow
    ~col_idx:child_col_idx ~new_val:Row.V_null
) child_rows
```

Same change for SET DEFAULT, with `new_val:default_val`.

`cascade_update_col_in_tx` already calls `update_col_in_tx` internally then walks the FKs that reference the updated column — so this is purely substituting one call for another and gaining the recursive walk.

Note: only proceed with this test if `b(a_id)` is allowed as an FK target — usually FK targets are PRIMARY KEY or UNIQUE columns. If sqlocaml rejects this constraint at parse/sema time, simplify the test to track the SET NULL chain differently, perhaps via an explicit UPDATE on b.

A simpler test that still exercises the fix path: in `cascade_update_col_in_tx`, the SET NULL branch updates child column → without the fix, doesn't recurse; with the fix, recurses. Set up:

```
A: id PRIMARY KEY, val UNIQUE
B: id PRIMARY KEY, a_val REFERENCES A(val) ON UPDATE SET NULL
C: id PRIMARY KEY, b_id REFERENCES B(id) ON UPDATE CASCADE
```

UPDATE A SET val = val+1 — propagates as SET NULL on B.a_val. This is an UPDATE on B, so any cascading ON UPDATE on B.id fires. C references B.id which didn't change, so C is untouched.

The test scenario that actually exercises the bug:

```
A: id PRIMARY KEY
B: a_id REFERENCES A(id) ON DELETE SET NULL, b_pk PRIMARY KEY
C: b_pk REFERENCES B(b_pk) ON DELETE CASCADE
```

DELETE A — SET NULL B.a_id. But B's row stays. C references b_pk, not a_id, so C is untouched.

Where SET NULL recursion matters: the SET NULL is itself an UPDATE; if THIS UPDATE on the child's column has further FK ON UPDATE actions, they should fire. Schema:

```
A: id PRIMARY KEY
B: a_id REFERENCES A(id) ON DELETE SET NULL  -- B.a_id will get UPDATEd to NULL
C: c_aid REFERENCES B(a_id) ON UPDATE CASCADE  -- this is the descendent
```

For this to work, B.a_id needs to be UNIQUE or PRIMARY KEY. Adding UNIQUE:

## Task 3: Prepared statements counter tracking
