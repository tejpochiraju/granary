**Background:** SQLite has FK enforcement OFF by default (`PRAGMA foreign_keys = 0`). Only when a connection explicitly runs `PRAGMA foreign_keys = 1` does it enforce FK constraints. sqlocaml currently always enforces FKs, causing `fk_no_enforcement` to fail (the test inserts an orphan row expecting success).

**Plan:** Store an `fk_enforcement: bool` flag in `Cat.t` (the catalog, which is per-connection). Default = `false`. Guard all FK checks on this flag. Expose PRAGMA foreign_keys as a true getter/setter.

## Task 3: Fix ORDER BY after 3-table JOIN + GROUP BY (fixes three_join_count)

**Files:**
- Modify: `lib/sql/planner.ml`
- Modify: `test/test_e2e.ml`

**Background:** The failing query:
```sql
SELECT dept.dname, COUNT(emp.id)
FROM dept JOIN emp ON dept.id = emp.dept_id JOIN sal ON emp.id = sal.emp_id
GROUP BY dname
ORDER BY dname
```
returns `[sales|1],[eng|2]` instead of `[eng|2],[sales|1]` (ascending).

**Root cause:** In an aggregated query, the planner applies ORDER BY AFTER `Op_aggregate`. The sort keys are translated from the sema's `bound_order_key.key` (a `BE_col i` where `i` is the pre-aggregation column index). In a 3-table join, `dname` is at pre-agg index 1. But after aggregation, the output row is `[dname(0), COUNT(1)]`. The planner emits `P_col 1` as the sort key, which refers to COUNT, not dname — causing wrong ordering.

**Fix:** When building sort keys for an aggregated query, translate pre-agg column indices (`P_col i`) to their post-agg output positions using the `group_by` column list and `agg_proj` projection items.

          | Plan.P_col i ->

             | Some out_pos -> Plan.P_col out_pos
             | None -> e)
          | _ -> e
        in
        (e', dir, nulls)
      ) order in
      if keys = [] then projected
      else Plan.Op_sort { keys; child = projected }
    end

**Background:** `INSERT INTO dest [(col1, col2, ...)] SELECT ... FROM src` is a very common SQL pattern for copying/transforming rows. Currently the parser only accepts `INSERT INTO t VALUES (...)`.

- Exec materializes the source stream via `to_list`, then inserts each row using the existing `execute_insert` machinery (with `~prebuilt_row`).
- db.ml: trigger hooks for the destination table's INSERT triggers.
